# Data model

The schema is organised so that the instrument's epistemic commitments are
enforced by structure rather than by discipline. Where a rule could be a
convention in a coding guide or a constraint in a table, it is a constraint in a
table.

## The provenance spine

Two tables carry everything else. `runs` holds every analytical or collection
run with its module, its version, its complete parameter set, a hash of that
parameter set, an optional seed, and an identifier for the code that produced it.
`requests` holds every request issued against the government interface, whether
it succeeded or not. The parameter hash is canonical, so two runs configured
identically hash identically regardless of the order in which parameters were
written, which makes a configuration citable.

A run is closed with a status by a context manager, including when it fails, and
a failed run keeps its exception in the note field. A run left in the running
state is itself informative and should not be tidied away.

## The record, and the extraction as a separate act

`comments` stores the response exactly as returned, together with a hash of it,
the address that returned it, the retrieval time, and the request that produced
it. Nothing normalises in place. The integrity check rehashes every stored
response and reports mismatches, which is how tampering or corruption becomes
visible rather than inferred.

`texts` is separate from `comments` because extraction is an analytical act and
carries its own provenance. Each text records its source, whether the typed field
or an attachment, the extractor and its version, and a flag marking whether the
text field is a placeholder pointing at a file rather than content. The
uniqueness constraint spans comment, source, attachment reference, and extractor
version, so a re-extraction under a new extractor version coexists with the old
one instead of destroying it.

The placeholder flag is the single most consequential field in the schema for
interpretation. On the environmental dockets the median text field is twelve
characters, which is a pointer rather than a comment, and treating those records
as very short comments inverts the reading of the entire docket.

## Machine suggestion and human code kept apart

`commenter_codes` holds columns prefixed `pre_` for rule based suggestions,
including the named rule that fired, and columns prefixed `cal_` reserved for
human coding with the coder's identity and a certainty flag. Nothing automated
writes to a `cal_` column. Agreement between the two families is measured per
input before any machine assignment is scaled to the remainder, which follows the
practice already used in the sister instrument and the coding architecture in
Judge-Lord's codebook.

## Coordination at two levels

`clusters` and `cluster_members` hold detection output, keyed to the run that
produced them, so that re-running detection with different parameters produces a
second set of clusters rather than overwriting the first. `coalitions` and
`coalition_members` exist because a sponsor's technical comment, its exact core
form letter, and its personalised satellites are one lobbying effort and not
three. Treating clusters as independent observations inflates the sample, and
coalition is the unit of analysis for anything about organised participation.

Coalition membership deliberately admits both clusters and individual comments,
because the organisational submission that a campaign supports is usually not
part of any cluster.

## Rule text and triage, defined before they are needed

`rule_texts` and `citations` are present and unpopulated. They are defined now
because the schema should express the full design rather than the current phase,
and because the proposed rule text is already needed by the detector for
stripping quoted material even though preamble analysis is Phase six.

## Sampling as a reproducible object

`samples` records the strategy, the seed, the strata, the size, and a hash of the
member manifest. A sample that cannot be regenerated byte identically from its
seed and parameters is not a sample this project reports, and the manifest hash
is what makes that checkable by a stranger.

## Uniqueness, and one trap that cost a corpus

Two identity constraints in this schema span nullable columns, the identity of an
extracted text spans attachment_ref and the identity of a rule text spans
fr_document. Declared as inline UNIQUE clauses, both were inert, because in SQL a
NULL never equals a NULL, so the constraint could never be violated and a
conflict clause depending on it could never fire. The effect was that every
repeated extraction silently duplicated the corpus, forty rows for twenty
comments, and the detector then counted thirty two texts where sixteen existed
and clustered each text with its own predecessor. Both are now expression indexes
over COALESCE of the nullable column, and both have regression tests.

The general rule that follows is worth stating because it applies beyond these
two tables. Uniqueness that spans a nullable column is declared as an expression
index and never as an inline UNIQUE. Any module reading the texts table selects
one generation per comment, source, and attachment reference, since extraction
history is retained on purpose and therefore has to be selected rather than
assumed.

## Instrument self knowledge

`artifacts` records the known ways this record manufactures false findings, each
with a guard, which is the rule a new measure must satisfy before it ships. The
table is seeded with four entries, the geographic statistic that counted blank
fields as a value, the apparent complete anonymity that was an agency practice of
not populating name fields, the arrival classes that reconstructed posting
batches, and the identifier ordered retrieval that misidentified a corpus.

`corrections` records superseded claims with their cause. It is seeded with three
entries from the first instrument, the misidentified largest campaign of the 2022
labor docket, the reclassification of a platform worker mobilisation from
astroturf to sponsor framed grassroots, and the superseded synthetic text share
for the labor pair.

## One view that exists to prevent an omission

`v_retrieval_share` joins dockets to their retrieval status and computes both the
share of the posted record that has been stored and the share of the received
record that was ever posted. Report generation reads from this view, which is how
a proportion in a report cannot quietly lose its denominator.
